# 仮コード（provisional call-site sketch）— 器具としての境界決定

日付: 2026-08-07
状態: **決定 / 器具であり設計成果物ではない**

## 1. これは何か

利用者outcomeの背骨を、**呼び出し側から先に書く**短い非compile sketch。
「あったらいいAPI」を書くのではなく、**背骨を最短で通すために呼ばれる側が何であるべきか**を書き出し、
そこで実名が書けない箇所を欠落として露出させる器具である。

出力は**gap listと既知実装調査の検索対象**であって、API仕様でも設計決定でもない。

## 2. なぜ必要か（本日の実測根拠）

2026-08-07に背骨4粒を施工した際、主担当のcapsule欠陥が累計8件出た。うち少なくとも3件は
**呼び出し側を1行書いていれば発注前に露出していた**。

| 実際に起きた欠陥 | 呼び出し側を書いていれば |
|---|---|
| 幾何boundsのownerが不明のまま発注しかけた | `let g = ???(doc, t)` で「何がper-layer変換を出すか」が検索課題になる |
| **playhead不在をgrain 3実装後に発見** | `project_stage_geometry(doc, ???, tracks)` の時点で「時刻はどこから来るか」が露出する |
| wire時刻がf64秒になり落とし穴B-1を踏んだ | wire型を書く段でframe境界適合が問われる |

`AGENTS.md` の既知実装preflight（`MECHANISM CLASS / KNOWN IMPLEMENTATION SEARCH / CANDIDATES / ...`）は
規約として存在するが、主担当は本日2回これを飛ばしかけた。仮コードはそのpreflightを
**散文でなくコード形状で強制する**器具である。

## 3. 規約

1. **`crates/` へ置かない。compileしない。** 製品コードと取り違えられる場所に置かない
2. **実名優先**。survey済みで実在が確定した型・関数は本名で書く。
   `???` を付けてよいのは**本当に何も無い箇所だけ**である
3. **`???` の集合が成果物**である。これが既知実装調査の検索対象になる
4. **authorityにしない**。仮コードを根拠に発注・実装・schema変更をしない。
   closed orderのAUTHORITY欄へ仮コードを引かない
5. **退役条件**: 対応するclosed orderが編成された時点で、その部分は役目を終える。
   仮コード全体は`観察`履歴へ落とし、正本として残さない

## 4. 相互検証条件

仮コードの`???`集合は、独立に実施したnode surveyの`ABSENT`集合と**照合できなければならない**。

- 一致する → 双方の信頼度が上がる
- 仮コードにだけ`???`が出る → surveyの見落とし、または仮コードが不要な抽象を発明している
- surveyにだけ`ABSENT`がある → その node は背骨に不要（＝今は要らない）

**この照合を行わない仮コードは採用しない。** 照合が、希望的観測と事実を分ける唯一の手続きである。

## 5-0. 製品全体への拡張（2026-08-07 第2改訂）

**製品全体まで広げてよい。** ただし目的が変わることを明記する。

| 段階 | 目的 | falsifier |
|---|---|---|
| 背骨・M3（第1改訂） | **接続されているか** | `???` × node survey `ABSENT` |
| 製品全体（本改訂） | **決めたことが互いに噛み合うか** | `???` × decision-index |

decision-indexは234の`決定`を持つが、**主題からの逆引き**であって同時成立の検査ではない。
387本のreview文書は別々の時期・別々のレビューで書かれており、
**全決定が1本の呼び出し鎖で同時に成立するかは一度も検査されていない。**

### 検出対象（機能一覧ではない）

1. **矛盾** — 単体では正しい2決定が両立しない
2. **断絶** — Aの出力とBの入力を繋ぐ決定が無い
3. **孤児** — 決定が参照する型が存在せず今後もしない
4. **順序不能** — AがBのruntimeを要求し、BがAで開放される

一次成果物は**決定間の合成失敗リスト**である。

### 鎖の形（発明しない）

[creator-developer連続体決定](2026-07-22-creator-developer-continuum-decision.md)が定める
`Use → Tune → Compose → Inspect → Fork → Author → Publish → Reuse` をそのまま使う。
**この鎖自体が既決であり、器具が発明するものではない。**

### 追加falsifier

`???` を **decision-index と照合する**。

- 決定が実在するのに`???`を置いていた → **起草側の検索失敗**であり欠落ではない
- 索引にも正本にも無い → 真の未決

### 読み方の規則

- 索引行は**どこを見るかの特定にだけ**使う（索引自身が「要旨だけで設計判断しない」と警告している）
- 鎖を書いていて**意味の選択が発生したら、その時点で正本を開く**
- 索引の`運用/発注`行（LLM配分、validation lane、review規律）と
  task ID経緯行（`CU-*` / `G0-*` / `U3a-*` の枝番）は**製品意味を定義しないため触らない**

### 拡張に伴う封じ込め強化

製品全体のsketchは**分量ゆえに設計文書に見える**。本器具で最大のauthority汚染リスクである。

- 各ファイル冒頭に**非authority・非compile・器具である旨を明記**する
- closed orderのAUTHORITY欄へ引かない。仕様・schema・公開APIの根拠にしない
- 未決領域（Vismのcontainer / loader / schema / runtime等）で`???`が多数出るのは
  **失敗ではなく正しい観測**である。埋めようとしない

## 5. 範囲（第1改訂・M3段階の記録）

**M3の全利用者outcomeまで広げてよい**（2026-08-07改訂）。当初は背骨1本に限定したが、
初回起草で`???`が6件に留まり大半が実名で埋まった。62項目のnode surveyがinventoryとして
効いており、自由発明の危険は想定より小さい。

広げる目的は**seamを一度に全部見つけること**にある。背骨6粒ぶんのseamしか分からない状態では
40粒規模のdisjoint allowlistを事前割当できず、本日と同じ逐次発見に戻る。

ただし広げる時は次を守る。

- **未決意味を書かない**。survey が `ABSENT` または地図が `SPEC_ONLY` の箇所は
  `???` を置いて**そこで止める**。呼び出し側の形を発明しない
- M4/M5は**呼び出しが自然に現れた時だけ**書く。outcome側から要求されないM4/M5要素は書かない
- 器具の役割は seam の発見であって、欠落部分の設計ではない

## 6. 並列化について — できることとできないこと

仮コードの目的の一つは、真の並列可能面を見つけることである。ただし**上限は計画品質ではなく既決規律で決まる**。

本日の実測: 背骨4粒のうち**3粒が`rn_product_host.rs`を触り直列化した**。
`R1-GPU-BINDING`とHost ABIは実行地図が明示的に直列と定めた共有境界である。

ただし本日の直列化の大半は**規律ではなく現在のコード形状**に由来する。両者を混同しない。

### 6.1 本当に不可分なもの（既決規律）

- **Document mutationの順序**: 絶対規律4のsingle writer。順序と排他は減らせない
- **snapshot coherence**: 全consumerが同一revisionを読むという契約性質
- **GPU device/queue/surfaceの単一owner**: runtime resource事実
- **atomic commit arbitration**: [Controlled Microkernel決定](2026-07-25-controlled-microkernel-host-module-parallelism-decision.md)のkernel責任

### 6.2 不可分ではないもの（現在のコード形状にすぎない）

`WireIntentEnvelope`は本日15 fieldへ育ち、うち5つ（`phase` / `view_local_x` / `view_local_y` /
`sequence` / `frame`）は本日の3粒が追加した。どのintent kindも他kindのoptional fieldを背負う
union structであり、`match intent.kind`も単一blockである。

本日の背骨3粒（pointer / time / selection）は**意味的に完全にdisjoint**であるにもかかわらず、
同じstructと同じmatchを触るという理由だけで直列化した。**衝突は構造的であって意味的ではない。**

per-kind payload、module別snapshot寄与、intent routingの登録制へ分解すれば、
これらは file-disjoint になり得た。

### 6.3 既決原則との一致

Controlled Microkernel決定は「Coreを極小のtyped protocol kernelへ収束させ、
Host capability moduleを分離し、**共通contractが締結済みなら同じslotの複数実装、
異なるHost capability、consumerを並列に実装・検収できる**」と定めている。

したがって「Host ABIは直列だから並列化できない」は**誤り**である。
現行`rn_product_host.rs`の単一struct／単一matchは既決契約ではなく、
薄くする対象である。この分解自体を統合地図のnode候補として扱う。

仮コードの役割は、この分解可能面を**呼び出し側の形から先に見つけること**にある。

## 6.4 器具の位置 — 粒割りの前に置く（2026-08-08 追記）

### 順序

```
利用者outcome → 鎖（仮コード）→ seam特定 → 粒割り → capsule → 施工
```

**2026-08-07はこの順序が逆だった。** 粒を4つ施工した後で鎖を書いたため、
仮コードは**予防ではなく診断**として働いた。

### 実測根拠

`WireIntentEnvelope`は本日15 fieldへ育ち、うち5つは同日の3粒が追加した。
**各粒のcapsuleはいずれも閉じていた**が、意味的に完全にdisjointな3粒（pointer / time / selection）が
同じstructと同じ`match intent.kind`を触るという理由だけで直列化した。

粒を先に割ると、**現在のファイル構成をなぞる**ことになる。
既に太っているstructがさらに太り、責任がそこへ集積する。

鎖を先に書いてper-kind分解を試したところ**書けた**。
kernelに残るのは`runtime`と`projection_generation`だけで、**15 fieldのうち13がcapability側へ落ちる**。
先に書いていれば、3粒はallowlistが交差しない形で発注できた。

同日、grain 1（幾何投影）とgrain 2（pointer transport）は並列に走ったが、
**その根拠は主担当のfile-disjoint推論であって鎖ではなかった。**

### 粒の割り方

**allowlistは鎖のseamで切る。現在のファイル境界で切らない。**

seamは責任の境界であり、ファイル境界は実装の履歴である。
後者で切ると、責任が複数粒へ分散し、後から移動・置換できなくなる。

`N-ABI-SPLIT`を[成果駆動統合地図](../outcome-driven-integration-map.md)§4へ
背骨の粒ではないnodeとして立てたのはこの線による。

### なぜ鎖は可搬か

鎖は**runtime交換を越えて生き残る名前**で書かれる。

2026-08-07の実測では、presentation runtimeが egui → WebView → RN と3回変わり、
生き残ったのは Document / D2 / journal / command / projection である。
仮コードが使う実名（`push_set_position_key_value`、`SetPositionKeyValueRequest`、
`render_graph_cached`、`LayerSourcePlugin`）はいずれもこの層に属する。

**粒の記録（どのファイルを触ったか）はruntime交換で死ぬが、鎖は死なない。**
Stage×M5判定が「Provider席は実在する」と言えたのも、鎖が意味の名前で書かれていたためである。

### 限界（重要）

**仮コードは何も強制しない。** 強制するのは capsule と allowlist である。

役割分担は次のとおりで、器具の導入によって変わらない。

| 責任 | 担当 |
|---|---|
| どこに線を引くか | 鎖が示す |
| 線を引く | 主担当 |
| 線を守らせる | capsule / allowlist |
| 守られたか検査する | diff監査 / oracle |

2026-08-07に主担当capsule起因の欠陥が8件出た。
**鎖が見えていても書き落とせば同じ事故が起きる。** 器具は判断を代替しない。

## 6.45 鎖にもgateを置く（2026-08-08 追記）

### 順序の改訂

```
利用者outcome → 鎖 → 【鎖のgate】 → seam特定 → 粒割り → capsule → 【capsuleのgate】 → 施工
```

**gateは2箇所必要である。**問う内容が違う。

| gate | 問い |
|---|---|
| **鎖のgate** | 鎖が実コードについて言っていることは**正しいか** |
| **capsuleのgate** | 実装者が**自分で決めてしまえる未指定事項**はどれか |

### 実測根拠

2026-08-08、`N-OVERLAY-MINIMAL` capsule を capsuleのgateへ通したところ12件を検出した。
**うち3件は capsule ではなく鎖に由来する誤り**だった。

- surface owner の指定が実コードと矛盾（`HostGpuBundle`ではなく`StageGpuBinding`の stage 別所有）
- 行番号が実際と不一致（`:985/:995` → 実際は `:983/:992`）
- **指定した接合点では frame が既に consume・present されており、後段へ compose を挿入できない**

3件目が本質である。鎖から `draw_stage_preview(gpu, frame)` を seam と特定したが、
**呼び出し行だけを読み、呼ばれる側の内部を読んでいなかった。**

> **「呼び出し箇所」と「挿入できる継ぎ目」は別物である。鎖はこれを区別しない。**

### 鎖のgateが検査すること

`???` の有無だけでなく、**実名で埋まった箇所も検査対象**である。両方向に誤りうる。

1. **`???` が過剰でないか** — 実在するのに検索が届かず`???`にしていないか
2. **実名が正しいか** — 型・関数・引数・行番号が実コードと一致するか
3. **seamが本当にseamか** — その位置へ挿入できるか。
   呼ばれる側が値をconsumeして完結していないか
4. **実名で埋まっているが使えないものはないか** —
   実在するが**gate／停止線で禁止されている**もの

4は`OverrunMode`で実際に起きた。`TimeMap`は実名で書けるため`???`が出ないが、
`Loop`／`Black`は`require_freeze_overrun`でv1拒否されている。

> **器具は「無いもの」は見つけるが、「あるが禁止されているもの」「あるが挿入できないもの」は素通りする。**
> `???`が出なかったことは、そこが閉じている証拠にならない。

### 頻度 — 鎖の更新ごとに回さない

**鎖のgateは、その鎖が施工を駆動する直前に一度だけ回す。**

鎖は探索の途中で何度も書き換わる。更新のたびにgateへ通すと、
器具のコストが器具の価値を超える。

- 鎖を書く・直す・区間を足す段階では**gateへ通さない**
- **seam特定へ進む直前**に一度通す
- 通した後に鎖が実質的に変わったら、**変わった区間だけ**を再度通す

検査は**ざっくりでよい**。全行の照合ではなく、
**間違っていると施工が壊れる load-bearing な実名とseam**に絞る。

### 独立性

鎖のgateも**別familyへ出す**。鎖の起草側と検査側を同一familyにしない。
本日は鎖を主担当（Anthropic）が書き、gateをSol（OpenAI）が担当した。

## 6.5 利用者シミュレーションの限界（2026-08-08 追記）

未決の体験判断について、外部LLMへ**利用者を演じさせて困る場面を列挙させる**運用を試した。
別family 2レーン独立で実施し、判定は一致した（先例4/4と同方向）。

しかし**次の読み違えが起きた。**

シミュレートされた利用者は、**自分が知っているソフトの前提を持ち込む。**
両レーンとも「同じ素材を2箇所にコピーして別々に色調整する」を当然の作業として挙げたが、
これは**素材＝加工単位であるソフトでの回避策**である。

Motoliiは`ClipSource::Asset { asset: AssetId }`と clip ごとの `envelope.effects` により
**1 Assetを複数 Clip が別々の加工で参照できる**。ファイルをコピーする理由が無く、
**その場面自体が起きない。**

主担当はこれを確認せず、シミュレーション出力を設計論点として扱い、
存在しない問題を検討した。

### 運用規則

> シミュレートされた利用者が挙げる困りごとには、**他ソフトの制約に由来する回避策**が混ざる。
> **Motoliiの既決モデルでその場面が起きうるかを先に確認**してから論点にする。
> 起きない場面は論点にしない。

順序は次のとおり。

```
シミュレーション出力 → 自分の既決モデルで起きうるか確認 → 起きるものだけ論点 → 先例照合
```

**先人のソフトを見る前に、自分の既決を見る。**

### 器具として保つ範囲

シミュレーションは**論点の所在と、主担当が用意した選択肢の外**を出すことには有効だった
（本日は主担当の2択の外を9件出し、うち「差し替え時の属性不一致（尺／fps／解像度／alpha）」は
`GAP-3`が扱っていない領域だった）。

出力は`観察`であり、**採否根拠にしない**（`AGENTS.md`「LLMの賛同をauthorityや採用資格にしない」）。
体験の一次資料は実機確認である。
