# UI の余白・整列・寸法関係 — Claude へのレビュー引き継ぎ

日付: 2026-09-20。状態: **観察**。

## 依頼の目的

Motolii の UI を、細部まで組版が整った製品に見える状態へ近づけたい。
利用者の仮説は「個々の部品の問題より、統一したルールの欠如ではないか」。
対象は余白、整列、文字と部品の寸法関係。一般的な UX 論、機能再配置、操作方法の再設計へ話を広げない。

レビュー時には実窓の Create・Media・Inspector・Timeline を観察し、現行ソースと照合した。
以下の数値はソース上の論理寸法であり、画面の実測 px ではない。
並行作業中の未コミット変更があったため、ソースと稼働中アプリの完全一致は未確認。
画像はこの文書に添付していない。着手時に現在の実窓を確認すること。

## 中心となる判断

共通の部品・数値は既にある。しかし、部品を組み合わせた際の余白の役割、余白を決める場所、縮小時に保つ寸法関係が十分に統一されていない、という仮説と整合する。
単に数値を一か所へ集めること、一律に余白を増やすことでは解消しない。
以下は修正候補であり、採用済みの仕様や原因の証明ではない。現在の実装を再確認し、反例も見て判断する。

## 1. 数値の共通化から、役割の共通化へ

**確認した事実**: `EditorMetrics` には `s4 / s6 / s8` と、多数の別サイズがある。パネルタブ左右は5、Browserの主要な内側余白は8、Inspectorのカード内側は6。

**見た目の判断**: 見出し・検索欄・本文がそれぞれ独立に配置されている印象が残る。数値が異なること自体を欠陥とはしない。同じ役割か、異なる役割かを先に区別する必要がある。

**修正候補**:

- 面や選択色の端と、その上の文字・記号の端を分けて扱う。
- パネル内の内容が従う基準線と、子階層のインデントを定義する。
- 外周、部品内部、項目間、群の間という役割で既存寸法を選ぶ。
- 関連しない寸法まで一斉に変わる、汎用 `s6` 等の値変更だけで済ませない。

**参照**: `motolii/ui/lib/foundation/metrics.dart` の `EditorMetrics`、`workspace/workspace_view.dart` のタブ、`panels/browser.dart` の `_inset`、`foundation/panel_controls.dart` の `EditorCard`。

## 2. 親と子が余白を重ねて決めている

**確認した事実**: Inspector の `_line` は下余白6を持ち、`EditorCard` も内容の末尾へ4を追加する。最後が通常行なら末尾は合計10になる。別形式の子では同じ合計になるとは限らない。

**見た目の判断**: セクションの終端の空き方が、内容の種類に左右される仕組みがある。10という値そのものが悪いという指摘ではない。

**修正候補**: 行は自分の高さを持ち、並べる親が行間と外周を持つ。末尾に何を置いても、同じ役割の空間は同じ規則で決まるようにする。

**参照**: `panels/inspector.dart` の `_line / _transform`、`foundation/panel_controls.dart` の `EditorCard`。

## 3. 縮小時に文字と周辺余白の比率が崩れる

**確認した事実**: Browser の `ShelfTile` は文字サイズに下限9を設ける一方、キャプション帯の高さと左右余白は倍率に比例して縮む。

| 寸法 | 100% | 60% |
|---|---:|---:|
| キャプション文字サイズ | 11 | 9（下限） |
| キャプション帯の高さ | 28 | 16.8 |
| 左右余白 | 4 | 2.4 |

**見た目の判断**: 実窓の60%表示では、図形・写真の領域に対して名前の帯が窮屈に見える。これは画面観察と計算が整合する事例で、改善後の比較は未実施。

**修正候補**: 文字の下限と、それを囲む帯・余白の下限を組として設計する。画像サイズとラベルの組版を切り分けて扱う。すべての倍率で同じ比率にする必要はないが、縮小時の成立条件を決める。

**参照**: `panels/browser/tile.dart` の `captionSize / captionHeight / air`、`panels/browser.dart` の `tileScale / BrowserSize`。

**注意**: Inspector下端の69%は `inspectorCell` の幅を基準128に対して表示した値。パネル全体や文字が69%へ縮小されている、という意味ではない。Browserの倍率と混同しない。

## 4. 箱の中心と、図柄の見た目の中心は別

**確認した事実**: Create のプレビューは、文字で描いた図形（サイズ23）、アイコン、32の箱の中の独自描画が混在し、中央配置されている。

**見た目の判断**: 塗りの四角・丸と、細い立体の線画でセル内の存在感が揃い切っていない。同じ外枠や中央配置だけでは保証できない。

**修正候補**: 塗り・線・文字の記号それぞれについて、占有範囲、線幅、視覚的な中心の基準を持たせる。対象を一つずつ見るだけでなく、棚全体で比較する。

**参照**: `panels/browser/create_shelf.dart` の `CreateShelf.preview`。

## 引き継いではいけない前回の断定

- 「Scale中央の空白は配置未完成」: 根拠不足。連動中のY欄を空け、他行との列位置を維持する実装がある。空白を埋めることを修正目的にしない。
- 「Dot帯が両端まで塗られていることが悪い」: 根拠不足。面を端まで伸ばすことと、内容の内側余白は別に判断する。
- 「小さいから大きくする」「色が多いから減らす」: 今回のレビューの結論ではない。

## 優先順位と確認方法

1. 余白の役割と、それを決める親・子の分担。
2. 縮小時の文字・帯・余白の連動。
3. 記号の視覚寸法。

共通部品で規則を表現し、代表画面へ適用して確かめる。局所の数値補正を増やす前に、その問題がどの共通規則に属するかを説明する。

- 同じ文書・選択・パネル幅・倍率で変更前後を比較する。
- Browser は少なくとも今回の60%と基準100%を確認する。
- Inspector は数値行と背の高い部品、異なる末尾を持つセクションを比較する。
- 各指摘について「実窓の観察」「コードで確認した事実」「修正仮説」「変更後の結果」を分ける。
- 合格は数値の統一や静的検査だけでなく、実窓で寸法関係が揃ったことをもって判断する。

現在の密度・配色・機能構成を出発点とし、今回の依頼から必要性を説明できない変更は混ぜない。既存の並行作業・未コミット変更を保全する。
