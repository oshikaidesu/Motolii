# UI の見た目を先例に基づいて詰める進め方(2026-10-01〜02 の実績)

Widgetbook 126 個を、約 1 晩で、「製品として採用できる」と判定された割合 92/126 から 122/126 まで引き上げた手順。
センスを私が持ち込むのではなく、**知識(先例)・測定・独立した判定**の 3 つに置き換えた。

## 0. 第一の規則: 作る前に探す
- 新しい道具・部品・依存を作る前に、全 branch・worktree、既存の依存、ネットの先例を探す。無いと確かめてから作る。
- この晩の失敗: 既に Widgetbook(`dev/ui-inspect` の `explorer/`、92 use case)があったのに、知らずに自作のカタログを書き、依存追加まで実行して止められた。

## 1. 先例を先に読む(判断の材料を外に置く)
- 書式は [awesome-design-md](https://github.com/voltagent/awesome-design-md) の 9 節(雰囲気 / 色 / 文字 / 部品 / 配置 / 深さ / Do と Don't / 応答 / エージェント向けの指示)。
- 数値は出荷済みの製品から取る: Adobe Spectrum のトークン、Blender の既定テーマ、Radix の暗いグレー、Linear、Raycast、Framer、Warp。
- 読んだ物と、開けなかった物(404、公開数値なし)を、両方書く。数値が見えた物だけを書き、推測には `[inferred]` を付ける。
- 成果物: `research/precedents.md`(先例ごとの数値、今の値との差、先例が割れている点)。

## 2. DESIGN.md に「出所の印」を付けて書く
- `[code]` ソースから / `[concept]` コンセプトアートから / `[decided]` 利用者が決めた / `[open]` 未決(値を書かない)。
- コンセプトアートは方向の参考。**絵の中で一貫していない細部(暗い線と明るい線が混在、など)は生成画像の揺らぎとして写さない。**
- 寸法は、参照と同じ単位(行の高さに対する比率)にそろえてから比べる。

## 3. 作業台は 1 つ(Widgetbook)
- 未決の問いは knob にして、利用者が実画面で選ぶ(行の高さ、縞の差、キーの縁、格子、Look)。
- 1 つの問いに 3 つの見た目(quiet / concept / glow)を並べる。1 案を作って直す、は避ける。
- 値は `tokens.dart` 1 か所に置き、部品は数値を直書きしない。

## 4. 並列で作る(担当ファイルを分ける)
- セット(再生・入力・ナビ・Timeline 部品・Relation・フィードバック・メディア・Stage)ごとに 1 エージェント。各自が自分のファイルだけを書く。
- 共有のトークンと主要部品は主担当が持つ。エージェントは `flutter analyze` だけを通す(起動はしない)。

## 5. 判定は独立した者に、yes/no で
- 判定者は別のサブエージェント。コードは直さない。
- 9 項目(階層・色の規律・深さ・一貫性・余白・読みやすさ・状態・仕上げ・製品の水準)を、Y か N で。N には具体的な観察を 1 つ。
- **測定の規則: 文字の大きさ・コントラスト・2〜4px の隙間は、拡大して実寸で測る。測れなければ `unverified`。** 縮小画面から読むと誤判定する(この晩は 9px と過大に報告された)。
- 利用者がまだ決めていない項目(軸の色、重大度の色、など)は N にせず `OPEN` と書く。

## 6. 指摘は担当に戻し、共通の不具合は主担当が直す
- N は元のエージェントに、具体的な修正として戻す(「CTA を 1 つにする」「余りを吸う Expanded にまとめる」など)。
- **同じ不具合が複数に出たら、共通の原因を疑う。** 例: 文字の下限が暗い文字(明るい地の上)まで持ち上げていて、6 か所が読めなくなっていた。
- 報告を鵜呑みにしない。直ったと言われた項目を、自分で画面を撮って確かめる(Render queue は報告と実画面が違い、`Spacer` が余りを吸わない設計の問題だった)。

## 7. 繰り返して、止める条件を決めておく
- 推移(採用できる / できない): 92/34 → 111/15 → 110/16 → 122/4 → 最終確認 8/10 → 全項目を画面で確認。
- 止める基準を先に決めた: N が 5 以下。基準を満たしたら、最後に 1 回だけ小さな確認をして区切る。

## 8. 利用者が決める項目は、一覧にして渡す
- `research/open-decisions.md`: 先例との差 10 項目と、暫定の値で動かしている項目(Look の既定、軸の色、再生・録画の色、重大度の色、アクセント色、危険の赤、工具の構成、文字の下限、選択の見せ方)。
- 暫定の値は、私が選んだのではなく、批評の結果に従ったものとして書く。

## この進め方で起きた失敗(繰り返さない)
1. 探す前に作った(偽の Widgetbook)。
2. 古い branch の窓を見せた(`git log --all` で直近の作業を先に確認すべきだった)。
3. 測った値をそのまま写した(生成画像の揺らぎまで)。
4. 縦の列の区切りを、行の区切りと読み違えた(利用者の指示を、画像と照らして確かめなかった)。
5. 共通の修正が、別の部品を壊した(上の 6)。
6. 起動の後始末で、起動中のプロセスを巻き込んだ(`pkill -f` がシェルごと止めた)。

## 規模の目安
- サブエージェント: 設計 8 + 判定 5 + 調査 1(各回の修正は元のエージェントを再開)。
- 画面確認: 判定 1 回あたり 300〜500 回の操作。
